# Milestone 1a: spec and core (plan)

- Status: waiting for the author's approval
- Target: November–December 2026
- Starts after: milestone 0 is done
- Done when (CLAUDE.md §5):
  - every refusal code the core can produce has a unit test;
  - every rule in the invoices declaration prints back in plain language;
  - core coverage is at least 90%;
  - the core has zero runtime dependencies.

No database in this milestone. Everything lives in `spec/` and `packages/core`.

## What gets built, in this order

1. **`spec/expressions.v1.md`**
   - Contents: the grammar (EBNF), types, empty-field semantics, money, dates, limits, and the plain-language phrase for every operator (record 0002).
   - It comes first because everything else uses it.
2. **Expression engine** in `packages/core/src/expressions/`:
   - tokenizer and parser that produce a small syntax tree, with errors that point at the position;
   - type checker against a type's fields;
   - evaluator with three-valued logic (true, false, unknown), as in Postgres `CHECK`;
   - plain-language printer.

   Tests come first:
   - one test per operator and per empty-field case;
   - money in the same and in different currencies;
   - date plus days;
   - the limits (length, depth);
   - the parser never throws anything except a parse error, tested with a few hundred generated inputs.
3. **Names:** valid names, intent ids (`invoice.mark_paid`), the MCP tool-name mapping (`invoice_mark_paid`), the collision check and reserved names (record 0002). One function, tested.
4. **`spec/declaration.v1.json`** (JSON Schema 2020-12) and the builder (`record`, `field`, `rule`).
   - The builder returns spec-shaped objects.
   - The core has its own validator, with no dependencies, that gives plain-language errors.
   - A test runs a set of valid and invalid declarations through both the core validator and the JSON Schema (ajv, as a development dependency) and checks that they agree.
5. **`spec/audit.v1.json`**: the audit entry format from records 0005 and 0006. Only the format in this milestone; writing entries comes in 1b.
6. **Example declaration:** `examples/invoices/keepwell/invoice.ts`, the declaration from §3.3 in final syntax. Tests use it.
7. **The core decision.** `decide({ declaration, actor, grants, intent, input, evidence, record, standingRules })` returns either `applied` (after-state, changed fields with before and after values, the rules evaluated and which fired) or a refusal. In pipeline order (record 0009):
   - permission
   - transition
   - field writers
   - input types
   - after-state
   - standing rules (record 0003; point 11 in `00.md`)
   - constraints
   - transition guards
8. **Refusals.**
   - One constructor makes every refusal, and it can't build one without `code`, `reason`, `rule`, `fields` and `next`. A test also checks this at runtime, for principle 2.
   - Reasons are written for a person who didn't write the rule.
   - `next` stays empty until milestone 5.
9. **`describe(declaration)`:** the plain-language text `check` will print later. A test checks that every rule in the invoices declaration prints.
10. **Gates in CI:**
    - coverage of `packages/core` at least 90% (Node's built-in coverage);
    - zero runtime imports in core (`check-imports` from M0);
    - one test per refusal code the core produces.

## Refusal codes and where they come from

| Code | Produced by | Milestone |
| --- | --- | --- |
| `actor_not_permitted` | core (permission) | 1a |
| `transition_not_allowed` | core | 1a |
| `field_not_writable` | core | 1a |
| `invalid_input` | core | 1a |
| `rule_requires_review` | core (standing rules) | 1a, if point 11 is approved; otherwise 1c |
| `constraint_failed` | core | 1a |
| `guard_failed` | core | 1a |
| `not_found`, `conflict` | runtime (load) | 1b |
| `rate_limited` | MCP and HTTP adapters | 3 |
| `duplicate` (an outcome, not a refusal) | runtime (load) | 1b |

## Risk

The expression language is the part most likely to grow. Anything beyond record 0002 (arithmetic, `today`, functions) goes into a new record and waits.
